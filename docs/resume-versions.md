# 多版本简历与岗位选择

同一个人可以保存“后端开发版”“Agent 开发版”等多份简历。每个版本拥有独立的 PDF 附件、基本资料、教育/实习/项目经历、求职偏好与确认状态；所有版本继续使用原资料 schema 和 macOS Keychain，不另建数据库。

## 客户端使用

1. 在“我的资料”导入 PDF。不同内容会创建独立版本，默认以文件名命名；文字版和扫描版继续使用原文字解析与本机 OCR。
2. 将版本命名为适合自己的名称，逐项核对并保存资料。版本下拉框用于切换当前编辑及默认使用的简历。
3. 在工作台选择岗位并点击“辅助填写”，选择本次简历版本，再确认网站资料披露。实际填写与 PDF 上传使用同一个选定版本。
4. 在任务抽屉查看本次简历名称与修订号。补充答案时，“仅本次申请使用”只作用于该申请及简历版本；“保存到本次所选简历”只修改该版本。

资料只在点击“确认并保存”后持久化。未确认的解析候选不会直接用于填写。切换到另一版本后，页面重新读取该版本的值，不会把前一个版本的编辑输入残留到另一个版本。

## 导入与修订

- 不同内容的文件，即使文件名相同，也会创建独立版本，避免把两种岗位方向的经历混在一起。
- 内容完全相同的文件重复导入，会定位到对应版本，保留该版本已确认值，并沿用原有冲突检测。
- 新版本不会自动继承其他版本的已确认资料、经历或 PDF；需要本人逐项确认。
- 版本名称可以修改。修订号会在该版本导入或保存资料时递增；修订号不是可切换的历史快照列表。
- CLI 可用 `profile import --update` 明确合并到当前版本。合并保留缺失字段的已确认值，冲突需要重新核对；客户端导入默认采用独立版本规则。

## 任务固定与恢复

开始填写时记录版本 ID、名称和修订号。任务运行中沿用跨进程锁，禁止切换、重命名、导入或编辑资料；CLI 与客户端遵守同一锁。任务暂停后恢复会重新观察官网页面，仍使用原版本和附件。

默认版本与某个岗位选用的版本可以不同。重新打开客户端时，申请记录仍显示原选择；再次启动该申请时优先选择之前的版本。

如果会话结束后资料被编辑，原来停在填写/审核阶段的任务不能悄悄换用新修订继续。请先在官网核查是否已经提交，再通过已有人工核查流程记录结果。结果未知的申请仍禁止盲目重试，也不会自动最终提交。

## 旧资料与安全存储

首次使用新功能时，已有的单份资料显示为“原有资料”。导入另一份简历后，旧资料仍作为可选版本保留，旧的 Keychain `profile` 条目作为迁移前备份保持原样。旧的导入次数不代表历史内容快照，因此无法自动恢复过去被合并覆盖的各份经历；需要把对应 PDF 重新导入。

版本索引与每份资料都保存在原 Keychain 服务中。保存时先写入新的资料条目并回读验证，再切换索引，避免索引指向只写了一半的数据；替代成功后清理旧的数据条目，原始迁移备份不清理。PDF 沿用原数据目录下权限受限的附件文件。SQLite 只记录任务选择和必要的导入摘要，不存储完整资料值；渲染层不使用 localStorage。

本次为兼容性扩展，无 SQLite 迁移，也不会创建新的数据目录。旧版程序不识别新的版本索引；回退到旧程序会读取保留的原始 `profile` 资料，不能看到后来新增的版本。请先停止任务再回退，不要让不同版本程序同时修改数据。

## CLI

```bash
npm run dev -- profile import /path/to/backend.pdf
npm run dev -- profile import /path/to/agent.pdf
npm run dev -- profile versions
npm run dev -- profile rename VERSION_ID 后端开发版
npm run dev -- profile use VERSION_ID
npm run dev -- apply JOB_ID --profile-version VERSION_ID

# 明确把一次补充合并到当前版本
npm run dev -- profile import /path/to/supplement.txt --update
```

`apply --profile` 仍仅用于 session 模式的临时结构化资料，不能与 `--profile-version` 同用。当前版本上限为 100 份，不提供删除或跨版本批量覆盖功能。
