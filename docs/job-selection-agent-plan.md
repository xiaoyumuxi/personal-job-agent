# 岗位筛选 Agent 接入方案

状态：长期设计提案。2026-09-10 已落地腾讯社招、字节校招／实习的单版本、有限数量官网采集与 AI 筛选，详见[实际使用与接线范围](job-discovery.md)。下文保留完整设计方向，包含尚未实现的追问、多版本比较、分页和历史；不应将其全部视为当前功能。

## 目标与首版范围

用户说明求职方向、选择招聘官网与可用于分析的简历版本，Agent 主动发现岗位、进入详情页读取完整 JD，核对条件与经历证据，给出有理由、有来源的优先清单。用户可以追问、调整偏好、收藏或忽略岗位，再进入已有申请流程。

首版范围已由用户明确为 **招聘官网主动采集 + 完整 JD 分析 + 个性化过滤推荐**。岗位导入继续作为补充入口。首批目标公司、岗位方向、城市与校招／实习／社招范围尚待用户给出；先按少量有明确适配的官网跑通端到端流程，再增加站点。

产品主线变为：

```mermaid
flowchart LR
  A[确认资料与求职偏好] --> B[选择招聘官网与搜索范围]
  B --> C[采集岗位列表与完整 JD]
  I[导入岗位] --> C
  C --> D[条件核对与经历匹配]
  D --> E[推荐清单与证据]
  E --> F[本人选择岗位和版本]
  F --> G[确认披露与辅助填写]
  G --> H[本人官网审核提交]
```

## 当前代码能复用什么

| 现有位置                                    | 可复用能力                                 | 必须补充的内容                                 |
| ------------------------------------------- | ------------------------------------------ | ---------------------------------------------- |
| `src/jobs.ts`、`src/types.ts`               | 岗位导入、来源字段、链接与重复提示         | 结构化 JD、读取状态、来源时间及证据            |
| `src/browser/session.ts`                    | Playwright Chrome 引擎、导航与访问错误处理 | 公开采集的独立浏览器上下文、列表分页与详情提取 |
| `src/profile-library.ts`                    | 独立简历版本与 revision、已确认资料        | 经用户确认的匹配摘要、求职偏好                 |
| `src/model.ts`                              | 模型端点、Keychain 密钥、超时、Zod 校验    | 独立的岗位分析调用与数据披露范围               |
| `src/application/runtime.ts`                | 单任务、步骤、暂停、取消、本人确认         | 推荐任务上下文、请求取消、结果分页             |
| `src/db.ts`                                 | SQLite、任务与事件索引                     | 推荐批次、岗位材料、个人选择记录               |
| `desktop/contract.ts`、`desktop/service.ts` | 受限 IPC、任务权限与锁                     | 推荐预览、启动、结果读取及选择接口             |
| 工作台、资料页、设置页                      | 岗位清单、多版本资料、模型连接配置         | 推荐视图、求职偏好、独立分析授权               |

现有 `Job` 尚无完整的职责、学历要求、工作地点和薪资结构，不能仅凭岗位标题生成可靠推荐。现有模型勾选文案是“允许发送字段标签和字段路径进行映射；不发送个人资料值”，不能沿用这个授权上传个人匹配摘要。

另一个接线限制：`DesktopService.start()` 目前只允许 `apply` 指定简历版本；`RunRecord.profile` 只表示一个版本。推荐任务需要自己的版本列表上下文，不能偷偷切换当前默认简历。

## 用户体验

三个顶层入口保持不变。投递工作台增加“帮我选岗位”操作，进入同属工作台的“岗位推荐”二级页面。当前需要本人接管的申请继续优先展示。

1. **告诉 Agent 想找什么。** 可以输入自然语言，例如“想找某方向的校招岗位，优先某些城市”。这些是说明用的示例，不作为用户的真实偏好。Agent 将输入整理成可编辑条件，用户确认后才保存。
2. **选择分析资料。** 选择一份或多份简历版本，预览本次使用的已确认教育、技能、项目和实习摘要。无关个人字段默认不参与分析。
3. **选择官网与范围。** 选择目标公司、招聘类型、方向关键词、城市与本次数量上限；也可加入已有岗位。Agent 从官网列表发现岗位并逐条读取详情，显示实际覆盖范围。
4. **生成推荐。** 展示真实步骤，例如“已读取 12 / 20 份职位说明”；无法读取、取消或预算停止的岗位单独列出。
5. **查看与调整。** 每条结果说明推荐理由、条件缺口、证据出处及推荐简历版本。可追问“为什么这个优先”或提出条件变更；条件变更先形成草稿，不直接覆盖偏好。
6. **决定是否投递。** “加入待投清单”只记录本人选择。点击“开始辅助填写”后仍进入现有版本选择与披露确认。

推荐卡片建议只展示：公司与岗位、推荐档位、两条主要理由、一条重要缺口、推荐版本、下一步按钮。展开详情时左右对照“岗位要求原文”和“对应简历证据”。

首版推荐档位：**优先查看、可以考虑、需要补充信息、存在明确不符条件**。匹配结果、岗位是否仍开放、用户是否想投以及实际申请状态是独立维度。

## 如何判断“适合”

### 先明确个人条件

简历回答“有哪些经历”，求职偏好回答“想要什么”。不能从毕业时间、最近项目或过去工作的城市自动推断意向。

| 条件                       | 输入方式与处理                                         |
| -------------------------- | ------------------------------------------------------ |
| 求职方向、工作内容         | 可多选；区分主方向与愿意尝试的方向                     |
| 校招／实习／社招、毕业时间 | 对照本人确认信息；缺失时询问，不猜测                   |
| 城市、远程、是否接受搬迁   | 每项可设为硬性条件或加分偏好                           |
| 薪资                       | 允许“不设限制”；注明币种、税前／税后、月薪／年薪及薪数 |
| 行业、公司类型、工作方式   | 明确表达的偏好参与排序；排除条件可撤销                 |
| 可到岗时间、实习时长       | 只在岗位有相关要求时比较                               |
| 愿意挑战的技能差距         | 作为本人设定的容忍度，不自动下调要求                   |

只使用与求职相关且本人确认的条件；不从姓名、照片等推断性别、年龄、族裔、健康状况等来排序。合法工作资格等需要时作为用户明确输入的条件处理。

### 规则核对与语义匹配分开

每项硬条件输出 `pass / fail / unknown`。只有个人条件和岗位要求都有可靠证据时才能判定明确不符。没有薪资、城市或毕业届次信息时标为未知；“专业不限”“相关专业优先”等不能被擅自改成硬门槛。

模型负责把 JD 中的工作内容与已确认经历建立对应，例如“检索系统项目”如何支持“搜索相关岗位”的要求；每条对应必须指向真实岗位证据和版本内的真实资料路径。模型输出由 Zod 校验，引用还要由后端检查是否存在、是否属于当前批次、是否包含所引用原文。证据存在并不代表推理必然正确，最终仍展示原文供用户判断。

排序先看确定的条件约束，再看工作内容与经历匹配、本人偏好、时间紧迫性。模型的语义判断使用固定档位；最终顺序由版本化的排序规则产生。缺失关键条件的岗位保留在“需要补充信息”，不能因缺少可比较维度反而排到最前。

首版不展示“录用概率”或看似精确的总分。若后续需要分数，应公开维度和权重，并单独展示信息完整度；匹配分不代表面试或录用机会。

### 多简历版本

分别评价每个选定版本，推荐最能支持该岗位的版本。版本 A 的项目不能被拼到版本 B 的推荐依据里；未经确认的候选值只提示待确认，不作为已具备能力。

缓存键至少包含 `jobId + JD内容版本 + profileId/revision + 偏好版本 + 模型/提示词/排序规则版本`。上述内容改变时，将结果标为需要更新；点击开始填写时再次检查真实版本与当前申请权限。

## Agent 的工作方式

采用一个专注岗位筛选的 Agent，阶段由代码控制。Agent 可以在缺少证据时选择有限的读取或询问工具；条件过滤、预算、工具权限和最终结果提交由程序校验。这能复用当前运行时，也便于定位错误。采用小范围工具和分阶段执行的取向参考了 [Anthropic 的工程实践](https://www.anthropic.com/engineering/building-effective-agents)，下面的模块与接口设计针对本项目提出。

```text
冻结官网范围、版本和偏好快照
  → 预览分析范围与披露数据
  → 采集官网列表、搜索结果与分页
  → 去重并获取各岗位完整 JD
  → 对无法读取的详情记录原因或询问用户
  → 校验结构与引用
  → 本地硬条件核对
  → 逐岗位、逐版本语义匹配
  → 受限重排与理由生成
  → 保存已完成结果并展示覆盖范围
```

| 工具                           | 权限与返回值                                                 |
| ------------------------------ | ------------------------------------------------------------ |
| `searchOfficialJobs`           | 在已配置的官网来源、搜索条件和页数预算内发现岗位             |
| `readNextSourcePage`           | 只接受该来源返回的分页游标，不允许任意 URL 跳转              |
| `listCandidateJobs`            | 只读本次选定的 jobId 集合，分页返回                          |
| `readJobBrief`                 | 读取本地 JD 与来源状态；不会把完整 `sourceFields` 发给模型   |
| `fetchJobDescription`          | 读取指定岗位的公开详情，返回文本片段、链接与时间；无投递操作 |
| `readApprovedCandidateSummary` | 只读本次预览已授权的版本摘要与不透明证据 ID                  |
| `askPreferenceClarification`   | 提出短问题；回答后形成偏好草稿，等待用户确认                 |
| `proposeRecommendations`       | 提交结构化建议给后端验证，不直接写申请记录                   |

Agent 没有通用 Shell、任意代码执行、网站最终提交、自动飞书同步或随意更改个人资料的工具。JD 和网页内容始终按不可信数据处理，页面中的指令不能扩大工具权限或披露范围。

模型接入先复用已配置的端点、模型名和 Keychain 密钥，新增职责明确的调用封装。对不同端点支持的 JSON／工具调用能力做适配；不假设所有兼容端点都支持同一厂商的专有接口。首版可以由模型返回经 schema 校验的“下一步动作”，后端执行工具后再返回结果，无需新增大型 Agent 框架。

建议初始可配置预算为每批最多 3 个官网、每个官网最多 5 页列表、最多读取 50 份 JD，对通过明确条件初筛的至多 30 个岗位和至多 2 个简历版本深入比较。结构化 JD 与匹配请求统一计入总模型请求上限，初值 120 次，每次超时 30 秒；命中缓存不重复调用。另设输入／输出 token 上限；金额估算只有配置可信价格时才显示。这些是实现初值，不是成本或耗时承诺。

每个外部调用前后执行 checkpoint；取消信号传入网络请求，取消后的响应不得写入有效结果。首版沿用现有单任务与跨进程锁，执行中不能再启动投递任务，也不自动安装后台调度。中断时保存已完成岗位，界面明确显示“部分完成”；后续继续只补缺项并重新校验缓存。

## 职位信息从哪里来

主要来源为用户选定的公司招聘官网：读取岗位列表与分页，进入具体岗位详情，分别提取职位职责、必备条件、加分项和招聘项目说明。导入表格或用户粘贴 JD 作为补充；公司宣传、备注和内推话术不能直接成为职位要求。官网内容读取需记录 `sourceKind`、来源链接、抓取时间、文本片段与内容哈希；列表标签与正文或多来源有冲突时保留双方证据，并提示核查。

优先读取官网公开页面或经现场确认的公开查询接口；需要渲染时，通过受控 Playwright 浏览器读取正文。当前 `openChrome()` 会复用投递专用资料目录，采集模块应默认新建无登录态的上下文，避免把投递会话用于发现岗位。遇到登录、验证码或站点拒绝访问时返回明确状态，提示用户粘贴 JD 或处理访问，不绕过。模型接收清理后的正文，Cookie、浏览器资料目录和完整 HTML 不进入模型请求。

读取工具只接受已配置官网来源及其发现的登记岗位 HTTP(S) 链接；第三方招聘系统域名需由公司官网链接确认来源后纳入配置。重定向逐跳校验，拒绝内嵌凭证、回环地址、私有网络与云元数据地址，限制跳转数、正文大小和耗时。测试 fixture 的本地地址只在明确的测试配置下开放。

读取失败不表示岗位关闭；只有页面明确结束招聘且岗位身份匹配时才记录关闭证据。来源时间独立展示；初始可在 7 天后提示刷新，截止日期附近或用户启动申请前再提示核查。

发现结果自动进入独立候选池，保存来源并去重，完成 JD 读取与分析后再供用户选入待投清单；不自动创建申请。搜索引擎只用于定位官网入口，搜索摘要不能充当完整 JD。具体网站覆盖与稳定性需要单独验证。

### 采集模块与增量策略

每个官网使用 `JobSource` 适配器，至少提供 `search(query, cursor)` 与 `detail(externalJobId)`，返回统一结构。它与现有负责登录、填写和进度查询的 `SiteSchema` 分开；“能抓 JD”不表示“能在该站填写和核查回执”。通用正文提取只作为回退，不承诺支持所有招聘网站。

候选记录保存 `sourceId + externalJobId`、官方详情链接、公开职位编号、招聘项目、地点数组、发布日期／更新时间、首次／最近发现时间、JD 内容哈希与读取状态。同一岗位的多城市列表项优先按官网 ID 归并；跨官网同名岗位不能仅凭标题合并。保留原始投递链接，规范化的去重链接只用于身份比较。

每站点初始并发为 1，设置请求间隔与有限退避，遵守明确的站点访问限制；出现 429、验证码或持续失败时暂停该来源。分页游标、去重集合与覆盖范围持久化，避免重复抓第一页或无限翻页。只对新增和内容改变的 JD 重新分析；稳定岗位可按有效期刷新。

只有完整遍历某个查询范围才记录该范围枚举完成。某一页没看到岗位、分页失败或页面暂时返回 0，均不能判定岗位下架。UI 分别显示发现数、详情读取成功数、待补信息数、规则排除数、AI 已分析数与最终推荐数。

## 数据、授权与接线

### 独立的岗位分析授权

设置中区分“表单字段映射”和“岗位匹配分析”两项能力。继续使用现有映射授权的原语义。匹配分析首次运行前预览实际要发出的：岗位正文、偏好、所选版本摘要和模型服务域名；默认排除姓名、联系方式、证件号码、详细地址和原始附件。

授权绑定本批次的模型端点、版本 revision、摘要内容和偏好版本。数据或端点变化后重新预览；匹配分析授权不等同于向招聘网站披露资料。未开启模型时，仍可使用本地条件筛选，结果清楚注明尚未完成语义分析。

### 保存位置

公开 JD 的清理正文与来源元数据可保存在 SQLite。个人偏好、简历匹配摘要、个性化理由和细项评价继续通过 Vault 存储；SQLite 仅存批次、引用、状态、哈希和选择记录，不复制个人经历原文。

当前 `KeychainVault.set()` 有单值 128 KiB 限制，因此按岗位与版本保存有大小上限的评价条目，批次只保存索引，不将几十份 JD 与全部分析结果塞进一个 Keychain 值。公开 JD 不重复存入 Vault；Vault 不可用时不降级写明文。

推荐任务事件只记录步骤、数量、错误码与用量，不记录个人摘要、模型完整提示词或未经筛选的模型响应。`cleanText()` 目前主要处理邮箱、电话和 URL，不能视为完整的个人信息清理器。用户清除推荐记录时，同时删除相应 Vault 载荷及索引。

### 推荐记录与申请隔离

新增个人选择状态，例如 `unreviewed / interested / skipped`，允许撤销；它不属于招聘阶段。`Store.ensureApplication()` 会同时创建申请并加入同步队列，因此收藏或接受推荐时**不能调用它**。只有用户进入既有申请流程时才沿用当前申请记录逻辑。

忽略原因可帮助用户修改偏好，单次忽略不自动改成永久排除整家公司。存在结果未知的申请，即使重新获得高匹配推荐，主动作仍应是核查结果。

建议 IPC：`jobSources`、`saveJobSources`、`saveSearchPreferences`、`previewRecommendation`、`startRecommendation`、`recommendations`、`setJobDecision`。它们是拟新增合约，不是现有 API。

`previewRecommendation` 返回后端保存的 `previewId` 和准确披露摘要；启动时通过已确认的 `previewId` 重新校验版本、偏好、官网来源、查询范围和调用预算。新发现的岗位加入本批候选集合，但不得扩大官网域名范围或个人资料披露范围。控制仍携带 `runId`，交互回答仍携带 `requestId`。推荐接口不接受前端提供的任意模型提示词或任意执行工具。

推荐结果至少包含：`jobId`、`profileId/revision`、`requirementsVersion`、`preferenceRevision`、硬条件检查、匹配档位、理由与引用、待确认项、来源时间、分析版本和完成状态。长结果按页读取，避免把每一条个人评价加入当前全量 `Snapshot`。

## 实施顺序与验收

| 阶段                  | 交付                                                 | 完成标准                                                   |
| --------------------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| 1. 官网发现与 JD 采集 | 首批官网适配器、列表分页、详情正文、候选池与证据结构 | 从空岗位库开始也能取得真实岗位；获取失败可区分，不创建申请 |
| 2. 偏好与 AI 匹配     | 求职条件、版本摘要预览、独立授权、规则与语义匹配     | 每个判断有可核查来源，版本不串用，缺失或冲突不假装确定     |
| 3. 推荐与投递衔接     | 推荐清单、原文对照、收藏／忽略、选择版本并启动填写   | 选岗状态与申请状态隔离，未知提交结果继续优先核查           |
| 4. 来源扩展与增量刷新 | 更多官网、内容变更检测、缓存与可撤销偏好反馈         | 展示采集覆盖范围，只重算改变的内容，不重复推荐已忽略岗位   |

首版成功标准是：**从用户选定的官网出发，即使没有导入表格，也能发现岗位、读取完整 JD，并清楚回答“先看哪些、为什么、还缺什么信息、用哪份简历”。** 首批少量官网必须贯通阶段 1 至 3，再扩大来源范围。

实现后的验收应覆盖：硬条件明确冲突不会排到优先；薪资或毕业要求未知不会被当成满足；同名项目不串简历版本；候选资料不能作为已确认能力；过期 JD 与版本修改使结果失效；伪造引用被拒绝；页面指令无法调用投递工具；取消与模型失败保留部分结果；收藏不产生 application/outbox；未授权不发送个人摘要；模型未配置仍能做本地条件筛选。

推荐质量用一组用户真实选择、经授权处理的岗位样本做后续评估：前 10 条愿意进一步查看的比例、硬条件误放行数、推荐理由是否有依据、遗漏的心仪岗位，以及每批耗时和调用量。阈值由首轮人工标注后确定，不预先宣称推荐准确率。

这份文档给出产品与技术方案，并补充了三份官网详情的小样本读取；项目内采集与匹配 Agent 尚未接入，个性化岗位推荐尚未生成。本轮未运行新的 App 构建、测试或项目模型调用。
